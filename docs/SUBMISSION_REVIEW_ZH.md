## 1. 我解决什么问题，服务谁

我设计 ClaimTrace，帮助小型电商卖家在发布中文商品文案前识别需要重点核查的宣传表达，并查找可追溯的历史案例。卖家输入一句文案，系统返回初筛标签、判断理由和可用引用；检索支持不足时，系统拒绝给出确定标签并提示人工复核。

我曾负责电商产品页面文案编辑。工作中，我会参考公司违禁词库检查文案，完成后再由上级复核；根据日常经验，检查一条文案通常约需 1–3 分钟，但我没有做系统计时。这段经历是 ClaimTrace 的问题来源。项目的主要目标用户仍是缺少专职合规人员的小型电商卖家；我尚未访谈这一用户群，因此不能把自己的工作流程直接当作他们的普遍情况，也不能声称系统已经节省时间或降低违规率。

本工具不提供法律意见、医疗或金融等专业决策，也不自动批准商品文案。普通商品广告中的治愈、疾病预防等危险宣传可以进入初筛范围。低风险不等于法律批准，所有文案正式发布仍需人工确认；“需要人工复核”只是提示，不代表已经派发工单或有人接收。

## 2. 为什么选择这一实现

我自建了 Streamlit 工作台、独立规则基线、案例检索组织、结构化响应校验和评估流程；复用现有 Python 库及多语言嵌入模型，通过 OpenRouter 使用基础模型服务。这是在“自己控制任务流程”和“购买通用模型能力”之间的折中，不是从零训练模型。

当前代码使用 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` 和余弦检索，返回三个最相近案例。原提案中的英文 MiniLM 与 FAISS 没有按原方案实施。面对现有 30 条案例，直接余弦检索降低了索引维护复杂度；本项目没有实测证明 FAISS 更差，也不把这一小规模选择推广到大规模场景。开发集的 10 条中文人工核验记录提供了有限的相关性证据，但不是总体检索准确率。

当前流程是规则比较、检索、阈值门控和最多一次模型评估，没有需要自主循环规划的任务，因此我没有实现 agent。规则基线是独立比较对象，不直接决定主风险卡。相似度低于暂定阈值 `0.30` 时不调用模型；恰好达到阈值时允许模型评估。阈值尚未充分校准，不能解释成违法概率。独立 LLM judge 是原计划中的可选项，本版本未实现；人工复核不能被描述为独立模型评审。

这一路线便于展示和验证，但依赖外部服务、嵌入质量和人工维护的案例库。Schema 校验能拒绝格式错误，却不能保证理由真实或引用有效。

## 3. 同一锁定样本上的结果与目标差距

我保留冻结标签和 30 条锁定测试记录：`high_risk` 12 条、`evidence_needed` 13 条、`low_risk` 5 条。它们是项目人工参考标签，不是监管机关标签。以下数值来自保存结果的只读重新核算，不是本次重新调用模型的结果。

| 口径 | 规则基线 Precision / Recall | ClaimTrace Precision / Recall |
| --- | --- | --- |
| 高风险专项：12 个正例 | 3/3 = 100% / 3/12 = 25% | 10/17 = 58.8% / 10/12 = 83.3% |
| 高风险＋需证据：25 个正例 | 8/8 = 100% / 8/25 = 32% | 17/17 = 100% / 17/25 = 68% |

第二种口径只把预测为上述两类的样本算作自动检出；`insufficient_evidence` 不算检出。我的原报告合并口径 80% 召回目标没有达成，不能用高风险专项的 83.3% 替代它。专项召回提升的同时，17 条高风险预测中有 7 条不是高风险参考标签；12 个高风险正例中每漏检一条，召回就变化约 8.3 个百分点，小样本不能支持稳定泛化结论。

> 【已测量，未达目标 G7】这不是缺少数字。必须解释 68% 与 80% 的差距，不得通过改标签、改分母或重写旧结果来宣称达标。

三类 Macro F1 在全部 30 条上计算，固定类别为高风险、需证据和低风险，拒答计入真实类别的未命中：规则基线 40.5%，ClaimTrace 48.0%。ClaimTrace 没有预测出 `evidence_needed`，这是重要局限，不能被合并口径隐藏。

ClaimTrace 已判断文案一致率为 13/20 = 65.0%，覆盖率为 20/30 = 66.7%，拒答／转人工提示率为 10/30 = 33.3%；三者不是同一个准确率。案例改写组一致率为 7/14，合成组为 6/6，但后者另有 9/15 拒答，不能称为“新文案准确率 100%”。案例改写与合成测试也不证明对全新真实案例的泛化。

## 4. 质量检查与剩余风险

20 条分层人工复核已记录为 completed，案例改写和合成各 10 条。其中 11 条有引用，10 条的引用被人工判断为支持风险提醒，支持率为 10/11 = 90.9%；另外 9 条没有适用引用，不能从分母中消失而不披露。这是所选样本的引用支持率，不是全部请求的引用正确率，更不是违法认定准确率。历史结果缺失下一步建议字段，20 条建议可执行性均为 not_applicable，仍未得到验证。

> 【待补证 G8】历史高亮片段和下一步建议没有保存，不能验证其质量或回填到旧结果；需要未来真实记录和人工检查，或明确披露此局限。

历史案例只能支持类比风险，不能证明当前商品承诺虚假。检索不足会让明显危险表达也被拒答，例如保存结果中的 CLAIM084；人工复核提示有助于避免强行确定，却不等于解决漏检。后续应在开发数据上检查检索与阈值，在新的独立样本上评估，而不修改锁定集来让指标变好。

## 5. 成本、隐私与是否值得继续

未来每次请求的模型成本可按 `输入 Token × 输入单价 / 1,000,000 + 输出 Token × 输出单价 / 1,000,000` 计算，单价必须对应实际模型、来源和日期。任务总成本还应包含其他变动成本、人工核查分钟数乘以人工分钟成本，以及固定开发／部署成本按真实任务数摊销。所有正式发布仍需人工确认，不能把 66.7% 覆盖率当作免人工率，也不能只给拒答样本计人工成本。

代码已经支持未来请求的最小用量日志，但没有本次正式测试的真实 Token、API 费用或延迟记录。这三项仍是“尚未测量”，缺失不是零。请求日志中的 HTTP 与解析时间也不等于包含检索和页面处理的端到端响应时间。本次离线演示不产生新 API 费用，不是商业运行成本测量。

> 【尚未测量 G5、G6】缺真实 usage、调用次数、成本和延迟；计划估算还需要对应模型的价格来源与日期。保留零费用路线不能生成这些真实测量；采集需单独批准样本、次数、费用上限和网络。

日志不保存完整文案或密钥，但真实评估请求仍会把文案和案例文本发送至外部模型服务；使用者不应输入敏感资料。当前没有完成数据转载授权、代码许可或全部历史秘密审计，不应直接宣称项目已经具备开源再分发条件。

> 【待补证 G11／提交前须完成 G2、G3】公开前核查来源、许可和秘密；当前截图及录屏脚本不等于视频，隔离工作版运行不等于最新 GitHub 交付。

我下一步优先补齐真实用户核查记录、可复现交付与诚实演示，而不是加入新模型、agent 或装饰功能。只有将质量改进、人工复核负担和实际成本放在一起，才能判断 ClaimTrace 是否值得进一步部署。
